## PL-1

**`trusted_proxies` — блокирует выход в production.**

Код готов (R8 этапа 2): `shop/runtime.php:53-63` (`rubizhClientAddress`). Значение по умолчанию — пустой список (`api/config.sample.php:5`). Пока список пуст, адрес клиента = `REMOTE_ADDR`, заголовок `X-Forwarded-For` игнорируется. **Риск, пока не установлено:** если хостинг проксирует запросы (ответ production ранее показывал `server: nginx`), `REMOTE_ADDR` у всех покупателей будет адресом прокси. Тогда сетевые лимиты (SMS, вход, заказы, общие лимиты запросов) станут **общими на весь магазин**: один активный посетитель может исчерпать лимит для всех.

**Что спросить у ukraine.com.ua** (письмом в поддержку):
1. Проходят ли HTTP(S)-запросы к `rubizh.shop` через обратный прокси/балансировщик/CDN перед Apache/PHP?
2. Если да — в каком заголовке передаётся реальный IP клиента (`X-Forwarded-For`, `X-Real-IP`, другой)? Добавляет ли прокси адрес клиента в конец `X-Forwarded-For` или перезаписывает заголовок?
3. Полный список IP-адресов/подсетей (IPv4 и IPv6, в CIDR) прокси, с которых приходят запросы на PHP. Стабилен ли он и где публикуются изменения?
4. Включён ли `mod_remoteip` (или аналог), который уже подменяет `REMOTE_ADDR`? (Тогда `trusted_proxies` должен остаться пустым.)

**Как проверить ответ** (только на тестовой копии сайта на том же хостинге, не на production): временный PHP-файл вне публичных маршрутов, который пишет в приватный лог `REMOTE_ADDR` и `HTTP_X_FORWARDED_FOR`; зайти с двух разных сетей (мобильный интернет и Wi-Fi). Ожидания: `REMOTE_ADDR` совпадает с IP из списка хостинга, последний элемент `X-Forwarded-For` — ваш реальный адрес. После проверки файл удалить.

**Какое значение куда вписать.** В приватный `api/config.php` хостинга: `'trusted_proxies' => ['<CIDR прокси 1>', '<CIDR прокси 2>']` — только подсети хостинга, никогда `0.0.0.0/0` или `::/0`. Если хостинг уже подменяет `REMOTE_ADDR` (`mod_remoteip`) или прокси нет — оставить `[]`.

**Тест после установки:**
- автоматически (до выкладки, локально/CI): `tests/stage2-r8-limits.test.mjs` «R8: forwarding is accepted only from explicitly trusted proxies and IPv6 uses /64»;
- на хостинге (тестовая копия): два устройства из разных сетей видят **разные** сетевые идентичности — исчерпание лимита на одном (например, запросов SMS-кода) не блокирует второе; поддельный `X-Forwarded-For` от клиента не меняет идентичность.

## PL-2

**Мобильная производительность — блокирует выход в production.** Решение по B/C — отдельной задачей **после этапа 3**, RC1 не меняется.

Текущие цифры (этап 2, вариант A выполнен — CSS gzip 44 107 → 30 974 байт, −29,8%; парные Lighthouse-замеры на одном хосте, мобильный профиль, медианы):

| Страница | Mobile score | LCP, с | TBT, мс | Desktop score / LCP |
|---|---|---|---|---|
| Главная | 54 | 7,42 | 712 | 90 / 1,50 с |
| Каталог | 51 | 7,01 | 923 | 92 / 1,49 с |
| Товар | 57 | 5,75 | 749 | 95 / 1,25 с |
| Комплект | 51 | 7,37 | 876 | 94 / 1,35 с |

Источник: `docs/release-hardening/STAGE_CHECKPOINT.md` (этап 2-B, Lighthouse A, код `f2264c6`). Замеры этапа 3 на финальном SHA — в Quality Gate (`STAGE_CHECKPOINT.md`, этап 3). Причина медленного LCP: первый экран рисует JavaScript (React-runtime + шаблоны `<x-dc>` из `index.html` ~283 КБ), а не HTML с сервера.

| Вариант | Суть | Объём (оценка) | Риск |
|---|---|---|---|
| B | Заранее скомпилировать runtime-шаблоны, уменьшить JS первого экрана (PERF-2.1, ~200 КБ) | средний: ~1–2 недели, сборочный шаг + перепроверка всех экранов | средний: меняется загрузка всех страниц; TBT снизится, LCP — частично (экран всё равно рисует JS) |
| C | Сервер отдаёт первый экран готовым HTML (главная, каталог, товар, комплект), JS «оживляет» его | большой: ~3–5 недель | выше: два пути рендеринга, риск расхождения разметки и цен; нужна полная браузерная матрица и проверка SEO/кеша |

**Рекомендация:** C для четырёх страниц первого экрана, поэтапно (сначала товар и каталог — там решение о покупке), с B только если он нужен как подготовка к C. Делать после RC1 отдельной веткой, с теми же парными замерами до/после.

**Ход работ (этап 5.3, 2026-10-17, ветка `hardening/stage-5.3b`):** CSP витрины без `'unsafe-eval'`; первый экран главной приходит в HTML; устранена лишняя загрузка десктопной картинки героя на телефонах. Главная (реальный троттлинг, медиана 3 прогонов): LCP 4,96 → 2,33 с, FCP 4,96 → 1,52 с, TBT 555 мс (> 300 — длинные задачи JS теперь после FCP). Каталог 6,4 с, товар 4,2 с, комплект 4,7 с — без изменений. Подробно — `docs/release-hardening/07-SECURITY_PERFORMANCE_REVIEW.md` §10. **PL-2 остаётся OPEN**: серверный первый экран каталога, товара, комплекта и разбиение первого рендера (TBT).

**Этап 5.5 (D-72, решение владельца): PL-2 остаётся блокером.** В 5.5 оптимизация не делалась — только измерение на реальных
посетителях: витрина анонимно отправляет LCP, CLS и INP (`assets/vitals.2026101801.js` → POST `shop/analytics.php`; шаблон страницы,
метрика, значение, телефон/компьютер, день — без IP, cookie, сессии и адреса; хранение 35 дней), CRM (только OWNER) — блок

`stage55-vitals`). Полевые p75 после закрытой выкладки и запуска — вход для 5.6.

## PL-3

**Смена `pim_key` и `cron_key` при выходе в production — обязательно, блокирует выход.** Основание: R1/R10 этапа 2 (история публичного репозитория не переписывалась; QA-20 принят владельцем как исторический риск).

1. Сгенерировать два новых независимых случайных значения (≥ 32 байт, например `php -r 'echo bin2hex(random_bytes(32)),"\n";'` на хостинге). Нигде не публиковать, не коммитить, не пересылать в мессенджерах.
2. Записать в приватный `api/config.php` хостинга (`pim_key`, `cron_key`).
3. Обновить ключ в PIM (настройка подключения к сайту) и в строке cron на хостинге (вызовы воркеров с `cron_key`).
4. Проверка: `/api/pim/status` со **старым** ключом → 401, с новым → 200; воркеры cron отрабатывают (журнал без 401); запрос воркера со старым `cron_key` отклоняется.
5. Описание ключей — [CONFIG.md](CONFIG.md).
