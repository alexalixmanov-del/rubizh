# CRM business rules

P0 remains mandatory: see [ORDER-P0-HARDENING.md](ORDER-P0-HARDENING.md).

* The existing `shopValidateOrder` is the common checkout, SKU resolution, confirmation, item quote and invoice validator. Resolve only owned active REAL SKU candidates. Recheck MODEL/COLOR/SIZE, stock, availability, price, submission/payment flags and confirmation requirements.
* Changed price returns `PRICE_CHANGED`, with the new quote and quote hash. OWNER must accept that exact hash with a reason. A manager cannot approve a reprice, including a SIZE_OPTION that acquires its first actual price. No invoice is created while any blocker remains.
* An eligible manager invoice requires canonical CONFIRMED. Active payment links are reused only after the same revalidation. A normal staff action cannot set PAID; only verified signed bank evidence or the existing OWNER proof workflow can do so.
* Unpaid cancellation releases the existing ACTIVE reservation. Unpaid expiry expires it only when no unresolved bank operation holds it. Signed PAID commits it once. Replay, duplicate callback, fulfillment and refund do not allocate a second reserve or release COMMITTED stock.
* Refund amounts are integer minor units. The cumulative successful amount cannot exceed the verified invoice amount. A durable `processing` intent commits before MonoPay is called. Unknown results hold the balance and prevent new refunds; retrying the same key returns the recorded operation and never calls the provider again.
* Correlated signed cancellation facts need exact invoice, extRef, amount and currency. An unattributed reversal cannot turn a partial refund into a full one. The old full-refund path rejects an invoice already managed by the ledger.
* A physical return checks cumulative quantities across non-rejected return requests. Its expected refund value comes from the historical discounted financial line allocation. Server-calculated `refund_minor` is retained per returned line; the final returned quantity receives the remaining minor units, so rounding never exceeds the historical line value. Older return records without this evidence require review instead of a guessed allocation. Zero-value physical returns cannot enter REFUND_PENDING. Closing REFUND_PENDING requires exact successful refund allocations; allocated amounts cannot be credited to another return twice.
* Physical return and stock restoration are separate. OWNER records KEEP_COMMITTED or PIM_RECONCILIATION_REQUIRED with a reason. CRM never invents a PIM stock movement; a PIM reconciliation decision must be completed by the inventory authority.
* Parcel allocation uses the existing NP rules for quantities, supplier and announced value. Actual package weight and dimensions are mandatory. Staff explicitly verifies packing; separate parcel delivery costs require buyer agreement. A draft is safe to cancel; unknown remote TTN results require reconciliation before another attempt.
* Notes append only, never appear in customer-facing receipts, and are rendered as text. Assignments and mutating forms use a current server version. Financial reasons accept 6–400 characters and reject control characters.
* Financial reports use signed successful payment events and audited transfer proof, then subtract successful refund facts. Pending order totals are never revenue. Date windows use Europe/Kyiv and convert to UTC server-side.
